## G1 — TickTree, learned directly from source (not just the README)

Read `ticktree-core`'s architectural spine directly (`BehaviorTree.java`, `AbstractNode.java`,
`Composite.java`) and the FTC bridge's two most load-bearing files (`OpModeTreeRunner.java`,
`CommandAction.java`), plus `docs/core-concepts.md` in full. **"Pre-alpha — API unstable" (the
repo's own words) applies to every finding below — none of this is a promise about a stable 1.0
API, all of it could change.**

**What the library actually is, confirmed from source, not just the README's description:**
- `BehaviorTree` is a deliberately "dumb driver" seam — binds a root `Node` + `Blackboard` once,
  exposes zero-arg `tick()`/`halt()` matching OpMode's `loop()`/`stop()`.
- `AbstractNode` centralizes the activation lifecycle (`onEnter`/`doTick`/active-flag/`lastStatus`)
  specifically to prevent "tree state leaking across ticks" — named as a known behavior-tree pitfall
  in their own design doc, engineered against directly, not incidentally avoided.
- `OpModeTreeRunner` is composition-only by deliberate design — "TickTree does not provide a base
  class to extend (it sits above what you already have)." `runLinear()` halts the tree on ANY exit
  (including `InterruptedException`, which it does not swallow); the iterative-OpMode path has no
  wrapper at all, by design, since the SDK calls the team's own `stop()` directly.
- `CommandAction` (the FTCLib/SolversLib bridge) is a real, deliberate design constraint: command
  leaves are **RUNNING/SUCCESS only** — a `Command` has no native failure signal, so "failure" must
  be expressed through tree structure (`Timeout`, `Guard`, `Condition`), never invented at the
  adapter level. It also **self-discloses** a real limitation in its own doc comment: no subsystem
  mutual-exclusion — nothing stops the same hardware being driven both via `CommandScheduler` and
  via TickTree at once if a team mixes scheduling paradigms for one subsystem.
- `docs/core-concepts.md` matches the code precisely on every point checked (memory vs. reactive
  composites, halt/preemption semantics) — no doc/code drift found in what was read.

**Refract-side findings** (how `ftc-construct` should account for TickTree's real current behavior,
once G3 makes it a real config option — not built this pass, recorded for that future work):
1. Generated LinearOpMode integration must use `OpModeTreeRunner.runLinear(tree, this::opModeIsActive)` after `waitForStart()` — never generate code that extends `OpModeTreeRunner` as a base class, it's composition-only by design.
2. Generated iterative-OpMode integration has no wrapper to call — must generate explicit `loop(){tree.tick();}` / `stop(){tree.halt();}`, and the `stop()` call is load-bearing (the actuator-stop guarantee), never omitted.
3. Any generated Command-leaf usage must never assume a `Command` can directly signal FAILURE — express it via `Timeout`/`Guard`/`Condition` wrapping, matching the library's own documented constraint.
4. The "never mix scheduling paradigms for one subsystem" constraint is a real generation-time safety rule — maps naturally onto `ftc-code-review`'s existing failure-mode-linting philosophy (state/authority-boundary bugs) and is a strong candidate for an actual lint rule once TickTree is wired in, not just a code comment.
5. Memory vs. reactive composite choice is, by the library's own description, "the single most error-prone idea in behavior trees" — any generated example must get this right by construction (guard conditions in `reactiveSequence`, priority arbitration in `reactiveSelector`), since a wrong choice is a silent behavioral bug, not a compile error.
6. The README's own `compileOnly`-dependency warning (FTCLib/SolversLib must be added by the team separately, not pulled in transitively) is a real setup gotcha `ftc-construct` should proactively check for when scaffolding TickTree-based code.

**TickTree-side findings** (real gaps to hand back to the TickTree project as genuine feedback, per
G4's split — never silently absorbed as a Refract-side workaround): **none found in this pass.**
This is an honest result, not a placeholder — everything read was well-documented, internally
consistent, and where TickTree has a real known limitation (the command-adapter mutual-exclusion

1. `OpModeTreeRunner` is composition-only — generated code must never extend it as a base class.
